# BALANCE-01: измерять ту игру, которую запускает пользователь

## Исправленная методика

Прежний tools/balance_lab.gd запускал стандартную стартовую колоду, затем заменял руки и порядок колод другим случайным генератором. Новая игра давно использует start_with_decks. Старые61,8% остаются исторической оценкой того эксперимента, а не доказательством нынешнего баланса.

Новый balance run начинает каждый матч тем же MatchCore.start_with_decks, что обычная игра. Не подменяет добор, монеты, порядок колоды или поле. Тест сверяет начальное состояние с отдельным стандартным запуском; каждый законченный матч заново воспроизводится по журналу. Правила D19-D21 и параметры30карт остаются прежними. Исправлен также прямой старый harness, а старый simulate:balance и experiment BALANCE-01 направляются в новую методику.

~~~text
scripts\chat.cmd balance plan
scripts\chat.cmd balance run
scripts\chat.cmd balance run --count 32 --seed 9001
scripts\chat.cmd profile-test balance-audit
~~~

## Циклы и реальное время

Поиск повторяющегося состояния учитывает всё, что влияет на следующий ход: очередь/монеты/поле/доход/ещё действующий этап роста/первый ход и состояние генератора стратегии. Исторические счётчики событий и номер уже насыщенного хода не скрывают фактический цикл. Для случайных стратегий состояние генератора обязательно: одна похожая позиция не означает бесконечность.

Специальная стратегия pass-only действительно обнаруживает повторяемый цикл после исчерпания добора. Она не включена в показатели баланса и не объявляется ошибкой существующего внешнего900секундного ограничения. Это положительный контроль самого детектора. В основных партиях лимит240команд записывается отдельно, не называется пятнадцатью минутами.

Цель человеческой партии около10минут и предел15минут требуют настоящих наблюдений человека. Headless runtime, число ходов и эмуляторный tap не закрывают эту часть BALANCE-01. Задача остаётся открытой до соответствующей проверки; нижеописанный выпуск может закрыть только инженерный инкремент.

## Возобновление

Расчёт разбит на блоки по4seed для каждой политики. Каждая часть имеет точный вход, хеш движка/исходников/протокола, журнал, результаты и квитанцию. Повтор пропускает только завершённые части с прежними байтами. Неполную чистую симуляцию разрешено пересчитать после сохранения предыдущего результата; неизвестная фаза и повреждённое доказательство блокируют повтор. Source-lock не разрешает менять тестируемые исходники.

По умолчанию команда выдаёт компактную сводку и пути summary.json / REPORT.ru.md. Ни результат concerns_observed, ни завершение скрипта не меняют принятые карты. Для настройки параметров нужен отдельный обоснованный эксперимент с контрольной и отложенной выборкой.

## Первичный источник

https://docs.godotengine.org/en/stable/classes/class_randomnumbergenerator.html - одинаковый seed повторяет поток, близкие seed лучше хешировать; внутренний алгоритм и корректные состояния генератора требуют аккуратного обращения. Движок и его бинарный хеш фиксируются в квитанции. Проверено28.09.2026.

Пороговые значения выше - предложенный инженерный протокол этой задачи, а не числа, взятые из документации Godot. Программная основа не зависит от обсуждений дизайн-лаборатории; новые дизайнерские гипотезы не принимаются через этот скрипт.
