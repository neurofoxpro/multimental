# Проверки → машинное ревью → dev одной командой

После штатного publish выполнить `npm run game -- github settle PR_NUMBER EXACT_HEAD_SHA`. На разрешённой станции эквивалент: `scripts/chat.cmd github settle PR_NUMBER EXACT_HEAD_SHA`. Команда ограниченно ждёт CI и завершает PR без отдельных ручных API-вызовов.

Входы: положительный номер PR и полный 40-символьный head. Принимается только PR из этого же репозитория, рабочая ветка feature/fix/docs/test и base=dev. Draft, другой head, неизвестная mergeability, незавершённые/упавшие проверки и запрос изменений не обходятся.

Обязательны успешные Build Android, Production controller, Cross-platform source quality и source-seal на точной паре base/head. После машинного COMMENT-ревью все проверки и refs читаются заново перед merge. Ревью не называется независимым человеческим одобрением.

Merge использует expected SHA и обычный merge commit. При неопределённом ответе сначала читается реальное состояние PR. Повтор уже завершённой команды не сливает PR второй раз. Никаких force-push, удаления файлов или обновления main.

После merge обычное push-событие запускает существующий dev build/release/Issue-memory. Команда выводит точную следующую команду `npm run game -- wait-dev MERGE_SHA`; это не доказательство уже законченного релиза. Установка — отдельная штатная delivery-операция и не блокирует merge при отсутствии телефона.

## Границы

В этом инкременте включён только локальный settle на существующей авторизованной станции. Запуск merge из GitHub Actions этим CLI отклоняется; постоянно работающий cloud-coordinator не включён. Маршруты github ship/cycle/release-dev ещё выключены: их старый dispatch-путь не соответствует текущему workflow. Не выдавать доступность одной команды за полностью автономную разработку после окончания чата.

Есть узкое окно между последним чтением base и серверным merge: REST принимает expected head, но не expected base. Фактический parent сохраняется в отчёте как baseChangedDuringMerge. Любой новый dev commit снова проходит проверку перед публикацией. Для полного серверного устранения гонки нужен отдельно настроенный merge queue/защита ветки, не фиктивная локальная гарантия.

## Проверки отказов

Тестовый клиент воспроизводит реальную последовательность read/review/read/merge/readback, потерю ответа merge/review, повтор завершённой команды, новый requested_changes, перемещение refs и перезапуск CI после ревью. Тексты Issues не исполняются, токены не печатаются, productionAuthorized всегда false.

Квитанция: `.gameprod/evidence/flow-cycle.json`, управляемый комментарий в соответствующем PR. Старый факт merge не означает новую установку или ручную приёмку.
