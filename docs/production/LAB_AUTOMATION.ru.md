# Автоматический тестовый цикл: lab

## Рабочий маршрут

`lab probe` наблюдает ADB, загрузку системы, имя выделенной AVD и физическую идентичность. USB и Wi-Fi одного телефона объединяются; серийные номера и адреса не попадают в публичную сводку. Недоступный транспорт и неудачное чтение свойств не выдаются за отсутствие всех устройств. Связь state=device сама по себе не означает завершённую загрузку Android.

`lab test` проверяет текущие инструменты через штатный `check`, предпочитает выделенный эмулятор, запускает его при необходимости, выбирает реально опубликованный dev-предрелиз, устанавливает его существующим проверенным updater и выполняет suite с возвратом в обычное приложение. Повтор `lab resume` сначала наблюдает фактический APK и входные хеши. Прошедшие тесты можно повторно использовать только при неизменных исходниках/установке/квитанциях.

| Запрос | Назначение |
|---|---|
| `lab test` | Виртуальная среда, полный базовый handoff-набор |
| `lab test --suite ui` | Быстрая проверка UI плюс нормальный запуск |
| `lab test --target available` | Известный основной телефон, иначе AVD |
| `lab test --target phone` | Только идентифицированный основной телефон; отсутствие — явный блок |
| `lab test --target emulator-B` | Точная выделенная виртуальная машина |
| `lab deliver` | Доставка на известный основной телефон без замены его другим устройством |
| `lab resume` | Продолжение одного зафиксированного цикла |

При `--commit` нужна полная SHA. Без неё выбирается последний подходящий dev-предрелиз и сразу фиксируется. Последующие этапы не перескакивают на новый опубликованный APK. Установка и suite используют существующие locks; дополнительно lab удерживает собственную станционную сессию и исходники. Нет параллельного изменения тестируемого дерева. Новый файл конфигурации создаётся только локально для конкретного запуска, основной station.local.json не меняется. У AVD собственное установленное состояние; личный профиль и ключ телефона не копируются в виртуальную среду.

## Беспроводной телефон

Физическое устройство узнаётся по его ранее сохранённой идентичности, а не по модели или IP. При запросе основной физической цели разрешён reconnect только к ограниченному набору объявленных private TLS-connect endpoints с service-name той же известной идентичности. После подключения свойства читаются заново. Pairing, `adb tcpip`, сброс сервера и отключение чужих устройств не выполняются. Другие авторизованные транспорты наблюдаются, но не становятся автоматически основным телефоном.

Регистрация второго телефона и единая установленная подпись остаются отдельной QA-02. Новый lab не запускает ранее отклонённые пакеты регистрации. Дополнительное физическое устройство не считается успешно обновлённым от одного наблюдения ADB.

## Возврат к ручной игре

У suite есть `--finish normal`. Последний шаг restore проверяет отсутствие pending automation-request, хеши двух поколений личного профиля, завершает только процесс Multimental Dev, запускает его заново, ждёт новый READY и foreground и сверяет профиль. Запросы и данные не удаляются. Это устраняет ложное ожидание нового READY при тёплом запуске процесса, который был запущен диагностикой.

Handoff-набор: close → launch → JNI → tutorial → UI → inspector → collection → restore. Каждый шаг имеет отдельную квитанцию, а один qualification lease удерживает одну установленную APK на весь набор. Прошедший restore после проваленного другого шага не превращает весь набор в PASS.

## Исследование и ограничения

Первичные документы, проверенные26.09.2026:
https://developer.android.com/tools/adb — state=device не равно boot completed, адресная цель -s и отдельное защищённое pairing.
https://developer.android.com/studio/run/emulator-commandline — именованные AVD, порты, запуск без окна и изолированная виртуальная среда.
https://developer.android.com/develop/ui/compose/system/shortcuts/creating-shortcuts — закрепление домашнего shortcut зависит от поддержки launcher и пользовательского подтверждения; оно не следует из install.

Поэтому эмуляторный PASS не означает Bluetooth по радио, реальный вырез экрана или дуэль двух физических телефонов. Новый lab не объявляет домашний ярлык созданным: это отдельное требование, которое надо закрывать фактическим launcher proof. Шаги ограничены по времени; таймаут и незнакомый lock сохраняют данные/журнал и не дают фиктивного результата. Полная AUTO-07 шире этого инкремента: все случаи оборванной подписи/установки требуют собственной приёмки.

## Readback после неопределённой установки

Реальный запуск показал: APK может установиться, но sleeping/keyguard не дать новому приложению вывести READY. Следующий цикл не устанавливает её повторно: проверяет фактический полный SHA-256 и versionCode, существующий проверенный signed artifact и постоянный сертификат, затем продолжает только launch. В журнале отдельно отмечаются install_pending, installed_readback, launch_pending и complete. Потерянный ответ install также сверяется с фактическими байтами до повтора. Изменённая same-version APK сохраняется и блокирует восстановление. Экран разрешено разбудить; штатный Android dismiss-keyguard не обходит PIN, пароль или биометрию. Требование credentials завершает этап явным блокером, а не фиктивным PASS.

Существующий updater при каждом вызове разрешает актуальный USB/Wi-Fi транспорт только прежнего физического primary и не перезаписывает station.local.json. Добавленные транзитивные модули входят в проверяемый deployment manifest.

## Наблюдение настоящего окружения

Windows ADB иногда выдаёт CRCRLF: общий adbLines теперь распознаёт уже загруженную AVD, не создавая второй несовместимый парсер. Живой процесс назначенной AVD_A может отсутствовать в ADB; такой слот занят, выбирается готовая B. Наблюдается только имя/порт/путь назначенной проекту AVD; чужие процессы не завершаются. device-status разрешает фактический USB/Wi-Fi transport без записи конфигурации и скрытого reconnect.

Для составления пакетов использовать Node JSON.stringify и сырые строковые шаблоны; PowerShell оставлять оболочкой запуска. Зарезервированные HOME/Host не использовать как переменные содержимого.
