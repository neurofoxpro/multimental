# Сохранение локального профиля

Профиль хранится в `user://profile/a.json` и `b.json`. Каждая копия содержит весь документ, номер поколения и SHA-256 точной строки payload. Новый результат записывается в неактивную копию; последняя проверенная копия не обнуляется. После записи выполняются flush, close, повторное чтение, проверка схемы и хеша. Успех возвращается только после readback.

## Восстановление и границы

При запуске выбирается новейшее корректное поколение. Незавершённая или повреждённая копия не становится профилем; при восстановлении предыдущего поколения показывается сообщение. Две повреждённые копии, неподдерживаемый формат, одинаковые поколения с разным содержимым или чужой profileId останавливают запись. Автоматического сброса профиля нет.

Восстановление резервного поколения может вернуть состояние до последней повреждённой операции. Это не обещание сохранить данные при любой аппаратной неисправности. Godot flush/close и проверенные модели обрыва процесса не доказывают физическую устойчивость диска к потере питания.

Хранилище рассчитано на одного писателя приложения. Повторный экземпляр с устаревшим хешем получает STORE_CHANGED_REOPEN; внутрипроцессная занятость тоже проверяется. Общая директория нескольких процессов или синхронизация облака этим механизмом не поддерживается.

## Транзакции без бесконечного журнала

`profile_journal.gd` использует монотонный sequence и окно 64 квитанций. Повтор с тем же sequence и тем же нормализованным JSON не повторяет результат; другой payload конфликтует. Номер за пределами сохранённого окна отвергается как старый, а не считается новой операцией. Поэтому старые запросы не получают повторную награду после сокращения журнала.

Старые произвольные ID из модели v1 сохраняются отдельно и не удаляются при переходе на последовательный поток. Контроллер хранит незавершённую операцию с её sequence; после неизвестного результата записи сначала перечитывает профиль. UI связывает результат с уникальным ID конкретной партии, чтобы повторный callback не посчитал матч дважды.

## Что сохраняется

Разделены inventory, decks, wallet, settings, stats, receipts/ordered и lastMatch. Пока коллекция, магазин и валютная экономика не реализованы, их данные не выдумываются и не начисляются. Завершённый обычный бой с ИИ сохраняет статистику и replay одной транзакцией. Локальные LAN/Bluetooth-матчи сохраняют только публичный итог: без руки противника, seed и скрытого порядка колоды. Это не полный сетевой replay. Обучение и диагностические режимы не увеличивают статистику; глобальный рейтинг отсутствует.

Язык переносится из существующего settings.cfg при первом создании профиля. Старый файл не переписывается; настройки звука остаются у AudioDirector. Старый last-match.json сохраняется на месте, но его результат не превращается в выдуманную статистику прошлых побед. Новые повторы боя находятся в транзакционном lastMatch.replay.

## Проверки одной командой

- `npm run game -- profile-test model`: исходная чистая модель.
- `npm run game -- profile-test storage`: запись, два поколения, повреждения, неопределённый результат и сокращение журнала.
- `npm run game -- profile-test ui`: реальная партия с ИИ, восстановление UI, язык, replay и повторные callbacks.
- `npm run game -- device-suite --target phone --suite profile`: настоящий диск Android в отдельной временной директории; хеши личного профиля не меняются.

Полный `check` включает все профильные наборы. Аппаратный профильный тест не требует Wi-Fi. Его временные файлы удаляются только из собственного случайного каталога; пользовательские копии a/b не удаляются. Повторная установка той же версии отдельно сравнивает число и SHA-256 уже существующих профильных файлов.

Симуляции оборванной записи и потерянного ответа помечены как fault injection, а не реальное отключение питания телефона. Автоматический профильный тест не является ручной оценкой интереса игры.

## Первичные технические источники

- https://docs.godotengine.org/en/stable/classes/class_fileaccess.html — FileAccess, flush/close, ошибки и SHA-256.
- https://docs.godotengine.org/en/stable/classes/class_json.html — JSON-преобразование чисел; хеш запроса считается после нормализации.

При последующей синхронизации аккаунтов локальные файлы не становятся доверенным источником серверной валюты или рейтинга. Серверная экономика и разрешение конфликтов — отдельные задачи.
