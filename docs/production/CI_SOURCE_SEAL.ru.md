# Точная идентичность проверенного PR

После успешного job Production checks workflow Build Android выполняет read-only job `Source seal BASE_SHA HEAD_SHA`. Он получает точный merge-checkout события PR, проверяет repository/PR number/target, GITHUB_SHA и ровно два Git parent: сначала base, затем head. Результат сохраняется в artifact `ci-source-identity`.

Проверка не принимает данные из названия ветки, текста Issue, произвольных аргументов или старого отчёта. Несовпадение любой части означает ошибку. Job не имеет permissions на запись, не сливает ветки и не публикует приложение. Успешная проверка PR в main не заменяет согласие владельца на main/stable.

Fork может проходить read-only тесты; это не делает его доверенным источником для автоматического вливания. Допуск merge отдельно ограничивает исходный репозиторий, ветку, актуальный head/base и отзывы. Проверенные старые комбинации не переносятся на новый base.

Файл `tools/ci-identity.mjs` проверяется в общем наборе Node-тестов. Положительные и отрицательные сценарии охватывают точные parents, перестановку parents, переехавший SHA, неподдерживаемое событие, другой repository, отсутствующий PR, неверный number и отсутствие публикационных полномочий.

Этот инкремент вводит недостающий source-seal, но сам по себе не включает автономный merge-flow. Прежнюю защиту в flow следует менять только отдельным проверяемым изменением, после фактического успешного job с точной идентичностью и проверки полной цепочки.

Основание различия head и merge-checkout: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows . Публикация от workflow требует отдельного запуска: события от GITHUB_TOKEN нельзя считать автоматическим push-триггером; явный workflow_dispatch является отдельным проверяемым маршрутом.
