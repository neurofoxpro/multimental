# Multimental — выпуск в Google Play

Проверка внешних технических требований: 25.09.2026. Это план и реестр допусков, а не подтверждение уже выполненной публикации. Канонический источник задач: `.gameprod/workplan.json`; статус `verified` там исторический. Команда `npm run game -- play-check` выполняет предварительную проверку инвентаря. Загрузка AAB и production-публикация пока НЕ реализованы и не запускаются этой командой.

## Две параллельные дорожки

Непрерывная разработка: идея → задача → эксперимент → код → проверка → PR → проверенный кандидат → dev → опубликованный APK → сохранное обновление телефона → ручная игра.

Полный Play-выпуск: закрытие согласованного объёма → production-подпись → AAB → проверка манифеста/нативных библиотек → internal testing → установка из Play → закрытое тестирование, если требуется аккаунту → одобрение владельца → production review → наблюдаемая публикация → наблюдаемое обновление из магазина.

Магазин/коллекция/крафт/новые механики не считаются готовыми только потому, что создан pipeline. Dev-сборки продолжаются между этими этапами. Неопределённую ранее основную механику и смысл рейтинга должен решить владелец; предложение агента не подменяет решение.

## 1. Аккаунт и бюджет: STORE-01/02

Сначала проверить существующий Play Console, тип и дату аккаунта, состояние верификации и доступ к production. Не просить завести новый аккаунт, если он уже есть. Если регистрации ещё нет, сбор и подтверждение личности/организации — отдельные действия владельца; бюджет «только бесплатно» не отменяется автоматически. До этого `.gameprod/play.json` честно содержит unknown/not_given.

Создать приложение и выполнить первоначальные действия, требуемые Console. Publishing API не рассматривается как способ обойти первичную регистрацию приложения. Принятие условий, документы, декларации аудитории и разрешение production не делегируются JSON-флагу.

В Cloud включается Android Publisher API, а сервисному аккаунту выдаётся доступ только к этому приложению в Play Console. Предпочтительны короткоживущие credentials через защищённое CI; долгоживущие ключи — только секреты с планом отзыва, не Git, не чат и не артефакт. Не давать лишние права на платежи/заказы/все приложения.

Источник настройки API: https://developers.google.com/android-publisher/getting_started

## 2. Подпись и идентичность: RELEASE-02

Сохраняются два разных приложения: `pro.neurofox.multimental.dev` для разработки и `pro.neurofox.multimental` для производства. Закрытый локальный dev-ключ не переиздаётся. Существующая установка .105.1 не удаляется и не очищается.

Сейчас исходный опубликованный dev APK и локально переподписанный APK имеют разные SHA-256. В отчёте сохраняются оба; это не одна и та же двоичная сборка. До массовой дистрибуции выбрать устойчивую схему подписи по каналу.

Upload key подписывает AAB для загрузки; при Play App Signing распространяемые APK подписываются app-signing key. Скачанный AAB нельзя установить обычным `adb install`. Play генерирует набор APK под устройство. Связь доказывается package/versionCode/source/AAB hash и отпечатком распространяемого сертификата, а не равенством AAB и APK.

Миграция тестового профиля в production — явный export/import с валидацией, не удаление старого приложения. Обновление APK несовместимой подписью должно останавливаться, а не делать автоматический uninstall.

Источник: https://developer.android.com/studio/publish/app-signing

## 3. AAB и платформенные проверки: RELEASE-03

Для новых приложений и обновлений обычного Android с 31.08.2026 требуется target Android 16 / API 36 или выше. Текущий dev CI использует API 35; production-профиль нужно обновить и реально испытать. Версия SDK сама по себе не доказывает target манифеста.

Перед RC повторно проверяется официальное требование, точный движок/templates/Gradle/JDK/SDK, arm64, `debuggable=false`, package без .dev, разрешения и возрастающий versionCode с учётом всех занятых версий Play. Рабочий Godot не обновляется попутно без отдельной проверки.

16KB принимается как внутренний обязательный инженерный gate: проверить ELF LOAD alignment всех .so, упаковку/zip alignment, bundletool validation и запуск на 16KB окружении. Наличие версии движка в README не заменяет испытание его native-библиотек.

Источники:
- https://developer.android.com/google/play/requirements/target-sdk
- https://developer.android.com/guide/practices/page-sizes
- https://developer.android.com/tools/bundletool

## 4. Декларации и материалы: STORE-03/04/05

Инвентаризация включает реальные данные и SDK: локальный профиль, диагностические логи, сети, аккаунт, синхронизацию и удаление. Нельзя написать «ничего не собираем» без проверки. Privacy Policy, Data Safety, App Access, content rating, ads declaration и права на все ассеты должны соответствовать фактической сборке.

Исходная аудитория «любой возраст» не определяет возрастной рейтинг и не разрешает незаметно сменить целевую аудиторию на взрослых. Декларацию возрастных групп и применимость Families подтверждает владелец. Паки сейчас покупаются за заработанную игровую валюту; реальные платежи и реклама не добавляются.

RU/EN store listing, иконка, feature graphic, настоящие screenshots и support/privacy/delete URL хранятся версионированно. Скрипты проверяют наличие, размеры, лимиты и ссылки; автоматически сгенерированные картинки не выдаются за скриншоты игры.

## 5. Контракт будущего publishing adapter: RELEASE-04

Одна защищённая цепочка должна выполнять: выбрать неизменяемый RC → проверить квитанции → создать edit → загрузить AAB/метаданные → проверить versionCode/hash → назначить согласованный track → validate → подтверждённый commit → readback.

Идентичность операции: repository, source SHA, rules/content versions, package, AAB SHA-256, versionCode, track, upload certificate, edit ID и deployment approval ID. Только ограниченный allowlist, argv без shell, один writer lease, конечные timeout, журналы без токенов.

Timeout записи не означает, что запись не произошла. Перед повтором commit/upload проверяется серверное состояние. Изменения через Console могут конфликтовать с edit; конфликт останавливает автоматизацию и сохраняет точную команду восстановления. Нельзя бесконечно создавать новые версии в ответ на неизвестный результат.

Internal и closed не означают разрешение production. Production требует явного одобрения владельца, защищённого окружения, неизменённого RC и актуальных подтверждений. Изменяемый агентом bool в `.gameprod/play.json` ничего не авторизует. `closeout` сейчас специально не способен выдать разрешение на публикацию.

Источник транзакционной модели: https://developers.google.com/android-publisher/edits

## 6. Реальные тестеры и магазинная установка: PLAY-01/02

Сначала internal testing и проверка именно магазинной сборки на авторизованном телефоне. Первый opt-in тестера, нужный Google-аккаунт и согласие в интерфейсе устройства — действия человека. После установки можно автоматизировать запуск, сценарии, диагностику и чтение package/version/certificate.

Если конкретному аккаунту требуется closed test, его число реальных тестеров и непрерывная длительность берутся из актуальной Console. Не заменять реальных участников эмуляторами и не сокращать реальное время поддельными отчётами. Если требование не применимо, сохранить подтверждение применимости, а не молча отметить passed.

Официальная проверка перед этим gate:
- https://support.google.com/googleplay/android-developer/answer/14151465
- https://support.google.com/googleplay/android-developer/answer/6112435

При этом аудите обе страницы Help не удалось получить полностью; численные условия регистрации и closed-test не считаются подтверждёнными только по памяти и должны быть перепроверены для аккаунта.

## 7. Production и поддержка: RELEASE-01, PLAY-03, OPS-01/02

Не смешивать состояния prepared, uploaded, submitted, in_review, approved, published, available_to_user и installed. После каждого перехода нужна настоящая квитанция API/Console/устройства. Срок и решение Google review не управляются нашим скриптом.

Поэтапный rollout и остановка при проблеме не откатывают уже установленные приложения. Исправление выпускается с большим versionCode, с сохранением данных. До первого production выполнить учебный цикл: дефект → задача → исправление → RC → тест → повторный выпуск.
