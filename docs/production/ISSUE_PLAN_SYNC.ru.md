# GitHub Issues → проверяемый снимок плана

Основная память — определения и обсуждения Issues. Файлы workplan/requirements/backlog/roadmap — версионируемый снимок, по которому можно проверять исходники без сети. Они больше не требуют ручного переноса статусов.

Команда: `npm run game -- github snapshot-plan` или `scripts/chat.cmd github snapshot-plan` на разрешённой станции и рабочей feature-ветке. После неё обычные `check` и `publish`; сама синхронизация не коммитит, не сливает ветки и не публикует сборку.

## Порядок

1. Прочитать точные текущие байты workplan и HEAD.
2. Получить полный live-снимок всех управляемых Issues.
3. Проверить уникальные ID задач и номера Issues, SHA тела определения, зависимости, критерии и доказательства verified.
4. Убедиться, что все readset/evidence файлы существуют; не принять новые задачи или сокращение Play-объёма молча.
5. Применить изменившийся план стандартным applyBundle с base HEAD и expectedCurrentSha256.
6. Сгенерировать производные документы и записать локальную квитанцию.

Потеря задачи, неверная ссылка и изменение исходника после чтения останавливают запись. Текст Issues — данные, не исполняемые команды. Закрытие Issue не подменяет содержимое её определения; исторический verified не даёт допуск новой сборке.

## Повтор и восстановление

При неизменных определениях source-write не выполняется и дата плана не меняется. Render выполняется всегда: после прерывания между применением и генерацией следующий вызов восстановит производные файлы без повторного изменения плана. Квитанция появляется только после успешного render.

`.gameprod/evidence/issue-snapshot-applied.json` содержит дату наблюдения, старые/новые статусы, номера Issues, хеши определений и исходный HEAD. Это не release approval. Для публикации изменения всё равно нужны стандартные проверки текущего исходника.
