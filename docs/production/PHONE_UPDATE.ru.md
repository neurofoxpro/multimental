# Обновление известного телефона одной командой

~~~text
scripts\chat.cmd phone honor
scripts\chat.cmd phone redmi
scripts\chat.cmd phone all
scripts\chat.cmd phone resume
~~~

При необходимости закрепить выпуск: phone honor --commit ПОЛНАЯ_SHA.
Без аргументов или с help команда только показывает справку, не выбирает произвольный телефон.

## Что сокращено

1. Не надо вручную искать IP, подставлять serial, находить номер последнего релиза и собирать цепочку команд. Выбирается известный Honor/Redmi, а не любой обнаруженный Android. Точная SHA опубликованного dev-релиза фиксируется на весь запрос. Docs-only HEAD не становится якобы новой APK.
2. Доступность запрошенного телефона проверяется первой. Если он недоступен, нет долгого check, сборки, эмуляторного review или установки на другой телефон. Возвращается not_ready с ссылкой на выбранный релиз. Для all доступные устройства обслуживаются, отсутствующие остаются явно незавершёнными.
3. Проверенный без изменений текущий рабочий срез повторно не прогоняет общий check. Изменившиеся инструменты обязательно проверяются. Для следующих запросов агент использует собственный уже проверенный срез, а не создаёт новую рабочую папку для каждого телефона.
4. Уже опубликованный совместимый manual APK проверяется и переиспользуется. Новый review запускается только при отсутствии подготовленного пакета. Конфликт хеша, подписи, публикации или конфигурации не маскируется повторной сборкой.
5. Установка и проверка телефона делегируются прежнему fleet ready: фактическая APK и подпись, сохранность профиля, обычный запуск, полный handoff, домашний значок. Установленные идентичные байты не переустанавливаются; неизвестный исход установки сначала сверяется с фактическим состоянием.

## Возобновление

phone resume использует прежние телефон, ID/тег/commit релиза, владельца, исходники и конфигурацию. Даже новый релиз с той же SHA, но другим ID, не подставляется незаметно. Изменившиеся входы требуют нового явного запроса. История каждой попытки лежит в отдельном .gameprod/evidence/phone-update/RUN_ID; указатель на последний запрос остаётся локальным.

Возобновление не выдаёт старый аппаратный PASS за новый: телефон снова проверяется через существующий fleet. Оптимизация касается контекста, проверки исходников, подготовки APK и повторной установки, а не удаления аппаратных критериев. Неизвестное действие не повторяется вслепую. При ошибке после установки сохраняется факт установленной APK и отдельная ошибка READY/ярлыка.

## Правила для агента

Использовать tools текущего dev и активный собственный claim. Чужую папку не занимать. Для повторного аппаратного запроса разрешено штатно получить новый claim в своей чистой, уже проверенной feature-папке командой collab claim QA-02 UNIQUE_ALIAS; прежний claim должен быть действительно released, source неизменен, область свободна. Не копировать verification receipt из чужого дерева. Новый source/ветка дизайна - новый проверяемый контекст.

Не включать TCP/IP5555, не сбрасывать ADB и не отключать Wi-Fi, через который идёт управление. Не менять станционную идентичность на случайный IP или другой телефон. Не удалять данные, не выдавать временную CI-подпись за обновление постоянной dev-подписи. PIN/пароль устройства не обходятся. Не ослаблять проверки журналов или запуска, когда они не проходят.

Если инструмент отказывает в действии, новая короткая команда не используется как альтернативный путь того же отклонённого действия. Отдельные изменения скриптов и тесты можно довести до результата, но факт установки на телефоне остаётся неподтверждённым.

## Проверка этой реализации

Регрессии запускают изолированные адаптеры без ADB: недоступный телефон, переиспользование проверки/пакета, испорченный артефакт, смена источников, ошибки установки, неподтверждённый ярлык и точный resume. Они не названы физическим испытанием Honor.

Первое наблюдение текущего запроса: Honor не находился среди доступных соединений. Дополнительный вызов подключения/наблюдения отклонён инструментом до подтверждённого выполнения. Новый маршрут не запускался для повторения этого отклонённого действия; установка Honor пока не заявляется выполненной. Базовый fleet и его проверки не ослаблены.

Команда печатает только этапы и короткую итоговую сводку. Полные журналы check/review/fleet сохраняются локально, не дублируются в контексте чата. Перед использованием отчёта дочернего fleet проверяются код завершения, новый runId, время и закреплённый commit: старый успешный latest.json не закрывает новый неудачный запуск.
