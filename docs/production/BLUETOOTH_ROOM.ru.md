# Bluetooth-комната 0.3.0 — границы кандидата

Используется та же RoomRules, те же роли/последовательности команд, приватная проекция и UI-обработчики, что в LAN. Различается только транспорт: защищённый Android RFCOMM с заранее сопряжённым устройством. Небезопасный RFCOMM не является fallback пользовательского режима. Старая лаборатория отдельно проверяет низкоуровневую передачу и не выдаётся за этот режим.

Пользователь разрешает доступ к устройствам поблизости, сопрягает телефоны средствами Android, создаёт комнату и лично передаёт приглашение. Гость выбирает уже сопряжённое устройство и вставляет приглашение. Wi-Fi/интернет не обязательны. Отмена системного pairing/permission не обходится скриптом.

В Windows тестовом клиенте выставляются SO_BTH_AUTHENTICATE и SO_BTH_ENCRYPT до connect. При отказе защищённого соединения испытание не переключается на незащищённое. Данные MAC и приглашение остаются в локальном request-файле; публичная квитанция содержит роль, версию, результат, источник и наличие защиты без идентификаторов устройства.

Headless BluetoothSession-тест использует fake-канал: он доказывает поведение протокола и переподключения, но не реальную передачу по адаптеру. Отдельный bluetooth-room-test проверяет реальный адаптер Windows ↔ телефон с выключенным Wi-Fi. Два физических Android-клиента в текущем комплекте устройств отсутствуют; такую аппаратную пару нельзя утверждать проверенной.

Android JavaObject имеет имя connect, совпадающее с Godot Object.connect для сигналов. Клиент использует runtime-вызов Java-метода без аргументов; ошибка/отказ остаются видимыми. Блокирующие connect/accept/read выполняются в рабочем потоке, закрытие сокета прерывает ожидание.

Первичные источники и их границы — .gameprod/research.json. До пройденной аппаратной квалификации этот файл описывает реализацию кандидата, не утверждает успешную доставку новой версии.
