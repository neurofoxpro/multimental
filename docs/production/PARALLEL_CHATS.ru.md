# Параллельные чаты Multimental

Основная память — Issues. Метки и блокирующие зависимости помогают выбрать работу; они НЕ являются атомарной блокировкой. Несколько чатов не должны менять ветку одного общего рабочего каталога.

## Единый порядок

`npm run game -- collab init` однократно создаёт служебную ветку coordination-state от известного dev. Код игры в эту ветку не разрабатывается и она никогда не вливается в dev/main.

`npm run game -- collab status` показывает актуальных владельцев задач и ресурсов. `npm run game -- collab start TASK-ID chat-unique-name` сначала проверяет полную память Issues и зависимости, атомарно закрепляет задачу/область, затем создаёт отдельный соседний Git worktree и устанавливает закреплённые npm-зависимости. Команда возвращает точный каталог и готовые команды. Существующий чужой каталог или ветка не перезаписываются.

Внутри возвращённого каталога: `npm run game -- resume`, `collab check-owner`, `collab renew`, затем обычные apply/check/publish/settle. После фиксации результата в задаче — `collab release`. До завершения задачи можно освободить срез, оставив явный комментарий о незавершённой работе. Release владения не закрывает Issue и не выдаёт ручную приёмку.

После закрытия PR следующий инкремент того же владельца начинается `collab branch короткий-суффикс`: ветка меняется только в его рабочем дереве, HEAD и текущие исходники сохраняются, переход журналируется. После release старый срез хранится как история; для новой работы нужен новый уникальный alias. Уже выпущенная ветка не используется для повторного PR.

Перед отдельными Godot-проверками готовится локальный кэш классов. Это исправление выявлено реальным запуском чистого среза: сначала UI-тест выявил отсутствующие типы, затем после импорта проекта прошёл.

`branch-recover plan|apply` — узкое восстановление только подтверждённо завершённого перехода ветки с отсутствующим PID. Оно сверяет текущую ветку/HEAD/claim и архивирует lock, не удаляя исходники и данные телефона. Общая операция не принимает pid/token/startedAt от вызывающего кода: эти поля принадлежат самой блокировке.

Временная недоступность GitHub останавливает новые записи. Локальный snapshot остаётся доступным для анализа. Не объявлять офлайн-кэш свежим разрешением на merge/устройство.

## Гарантия и ограничения

Состояние обновляется GitHub createCommitOnBranch с expectedHeadOid. При одновременной заявке на один ресурс победит один коммит. Второй читает новое состояние и не может получить уже занятую область. Все изменения журнала имеют operation ID и hash; после потерянного ответа выполняется readback, не слепой повтор.

Срок heartbeat 30 минут — диагностический, а не разрешение украсть работу. Просроченный владелец продолжает блокировать ресурс до явного освобождения/проверяемого восстановления. Иначе старый процесс мог бы продолжить запись после назначения нового владельца. Claim не является секретом: авторизация обеспечивается доступом GitHub, а не публичным token.

Это протокол для сотрудничающих агентов и строгих команд, не изоляция от произвольного администратора GitHub. Ручное редактирование coordination-state, обход команды Git и смена alias для захвата ресурсов запрещены инструкцией проекта. Историческая квитанция claim не даёт владение после release: оно проверяется по текущему state.

## Независимые направления

Автоматизация/координация, игровая экономика, UX-исследование, интерфейс и устройства получают отдельные области из `.gameprod/collaboration.json`. Экономика и UX-исследование могут идти одновременно; два изменения одного игрового UI — последовательно. Любой двухтелефонный radio-тест занимает оба телефона и радиоадаптер вместе. Существующая qualification-блокировка остаётся обязательной; новый claim не заменяет физическую блокировку.

Пока общая подпись/регистрация второго телефона не включена, одна видимая модель не превращается в два устройства. Не устанавливать в произвольный serial. Публикация dev независима от телефона; production по-прежнему требует разрешения владельца.
