# Рабочая очередь и воспроизводимое исследование

## Короткий цикл активного агента

```text
scripts\chat.cmd work plan --tag beta
scripts\chat.cmd work next unique-chat-alias --tag kind:automation
scripts\chat.cmd focus
scripts\chat.cmd study packet TASK-ID
scripts\chat.cmd study run TASK-ID
scripts\chat.cmd apply BUNDLE.json
scripts\chat.cmd ship
```

work next запускается из свободного/освобождённого среза и возвращает новый каталог. Перейти в него до изменения исходников. Одному чату принадлежит одна задача. После зафиксированного результата и accept нужной задачи выполнить collab release; только затем брать следующую. Пока в текущем дереве активна другая задача, next останавливается. Повтор после неопределённого ответа использует прежний журнал выбора и тот же alias, а не назначает другую задачу.

work plan читает актуальные управляемые Issues и GitHub CAS claims. Порядок определяется уже заданным численным приоритетом; при равенстве сначала задача, открывающая больше непосредственных зависимостей. Числа приоритета скрипт сам не переписывает. В одной предлагаемой волне до трёх задач с непересекающимися ресурсами. План не запускает LLM-агентов и не подтверждает аппаратную готовность.

Теги: beta, kind:ui, kind:automation, kind:game, gp:area:game-ui, gp:priority:p1, task:UX-09 и дополнительные task.tags. Несколько --tag объединяются условием И. gp-теги вычисляются тем же смыслом, что существующая GitHub-проекция, а не считаются mutex. Просроченные claims по-прежнему заняты; ручные/внешние/release-решения автоматически не берутся. Несогласованная закрытая Issue без verified тоже удерживается для проверки, а не выполняется заново.

## Новые задачи из найденных проблем

Агент оформляет небольшой конкретный пакет `.gameprod/ideas/NAME.json` с полными определениями tasks: источник, зависимости, критерии, readset, release-scope и приоритет. `work enroll FILE` вызывает существующие guarded enroll и идемпотентный github sync. Он не меняет авторские определения уже существующих Issues и не объявляет новые задачи выполненными. GitHub dev-push обновляет gp-метки и нативные зависимости штатной проекцией.

Задачи должны описывать обнаруженный пробел, а не бесконечно создавать работу. Сначала дефекты сохранений/правил/доступа, затем частые пользовательские действия, затем визуальная полировка. Уже принятые решения и отдельно отложенная особая механика не меняются.

## Исследование с проверяемыми стадиями

Определение `.gameprod/studies/TASK-ID.json` содержит вопрос, гипотезу, контроль, sources, точный readset, названия проверенных адаптеров, критерии и ограничения. `study check` проверяет определения офлайн и входит в общий verify. `study packet TASK` показывает хеши входов и первую неподтверждённую стадию без полного архива чатов.

`study run TASK` выполняет capture → checks → analysis. Capture ограничен официальными HTTPS-доменами, двумя параллельными чтениями, размером тела, числом переходов и временем. Каждый redirect проверяется до запроса. Текст страницы никогда не становится командой. Сохраняются URL, итоговый URL, размер и SHA-256, но скачивание не выдаётся за понимание источника.

Check запускает только фиксированные argv из проверенного реестра, без shell и без исполнения строк из Issue/HTML. PASS после runtime ERROR, пустой Node-набор, ненулевой exit code и изменение исходников отвергаются. При повторе пропускаются только успешные проверки с теми же исходниками и неповреждённым журналом; неполные источники сохраняются. Во время run общий source-lock не позволяет apply менять код.

Стадия analysis принадлежит активному агенту. Результат в `.gameprod/studies/results/TASK-ID.json` содержит inputKey, verdict supported/partial/rejected, conclusion, limitations и полный список sourceHashes. После guarded apply выполнить `study record TASK FILE`. Это не независимая человеческая приёмка. Аргументированное rejected — завершённое исследование, а не реализованная функция.

Checkpoint `.gameprod/evidence/study-TASK-ID.json` сохраняется после каждой группы источников и каждой проверки. Изменение входов, устаревшие источники или отсутствующая проверка возвращают к нужной стадии. Предыдущая квитанция архивируется. Сами записи определения и результаты не выполняются как код.

## Границы

Ни короткая команда, ни новый чат не обходят source-seal, точные head/base, dev CI, сохранность данных или ограничения main/stable/Play. Study — автоматизированный сбор и проверка доказательств, а не утверждение, что скрипт сам научно понимает тексты. Work — выбор и координация задач, а не работа модели после закрытия чата. Телефоны, ярлыки лаунчера и ручная оценка игры подтверждаются отдельно.
